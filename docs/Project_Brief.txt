    Machine Learning Portfolio Project
1. Project Task
Complete a focused Machine Learning investigation using an approved dataset. Your project should normally
address one classification or regression problem using techniques taught in the module. The aim is to
demonstrate a sound process, not to use the most complex model or obtain the highest possible score.
You must:
    1.   Define a clear problem and explain the dataset;
    2.   Prepare the data and design a valid evaluation;
    3.   Build and compare a small number of suitable models against each other;
    4.   Interpret the results, limitations and responsible-use implications.

2. What you will Submit
    •    Code or notebook: a complete, readable workflow that loads the data, prepares it, trains the models
         and produces the reported results. You should use an online repository to track and store all the
         work for this project.
    •    Detailed report: maximum 3,000 words covering the problem, data, methods, results, limitations,
         and conclusion.
    •    README and environment file: brief instructions for running the work, including required
         packages.
    •    Demonstration video: A 5 minute video (screen capture with voice over) demonstrating your
         project and explaining your main decisions, results and one important limitation.
    •    Assistance declaration: Identify any external code, collaboration, generative AI or coding-assistant
         use throughout the project.
Use an approved, appropriately licensed dataset. Do not submit confidential or uncontrolled personal data.
The submitted workflow must run using the instructions provided.

6. Exact Milestone Submissions
Submit each milestone through the designated Canvas assignment as a single ZIP file unless Canvas states
otherwise. Use the filename format StudentID_MilestoneNumber.zip.

Milestone 1: Project Proposal
Submit one PDF of no more than one page containing:
   •   the project title and a clear classification or regression question;
   •   the dataset name, source, licence and citation;
   •   the target variable and main input features;
   •   the approximate number of records and important data-quality issues;
   •   the proposed baseline, candidate models and evaluation metrics;
   •   one short paragraph on privacy, fairness, misuse or other responsible-ML risks;
   •   a link to the online project repository.

Milestone 2: Data and Baseline Checkpoint
Submit:
   •   a working notebook or source-code folder that loads the data and runs the work completed so far;
   •   a README with setup and run instructions;
   •   an environment or requirements file listing required packages;
   •   a brief data audit covering dataset shape, variable types, missing values, duplicates, target
       distribution and any obvious outliers;
   •   the preprocessing pipeline and explanation of the train/test split or cross-validation design;
   •   results for a simple baseline model using the proposed metrics;
   •   the repository link and a short assistance declaration.

Milestone 3: Model Comparison Checkpoint
Submit:
   •   updated runnable code or notebook;
   •   a results table comparing the baseline with at least two suitable learned models under the same
       evaluation protocol;
   •   the main model settings and a brief explanation of any tuning performed;
   •   at least one relevant visualisation, such as a confusion matrix, ROC or precision–recall curve, residual
       plot or feature-importance plot;
   •   a short error or residual analysis identifying where a model performs poorly;
   •   a draft conclusion stating the current best model, evidence, limitations and next steps;
   •   the updated repository link and assistance declaration.

7. Important Information
   •   The work must be your own and you must be able to explain all submitted code, results and decisions.
       Suspicious cases may lead to student interviews and could result with being referred to the School of
       Computer Science Academic Integrity Advisor for disciplinary action.
   •   Do not tune models using the final test set.
   •   Cite the dataset and any external code or sources.
   •   Declare any use of generative AI and coding assistants, and verify all assisted work.

8. Resources and Setup Guides
The following resources can help you find a suitable dataset and create a reproducible project. Always check
the dataset licence, documentation, provenance and ethical implications before requesting approval.

Finding an Appropriate Dataset
   •   UCI Machine Learning Repository: well-documented datasets for classification and regression,
       often with clear feature and target descriptions.
   •   OpenML: searchable datasets with machine-readable metadata, task types and links to previous
       experiments.
   •   Kaggle Datasets: a large collection of community and organisation-published datasets. Check the
       original source, licence and quality rather than relying only on the Kaggle description.
   •   data.gov.ie: the Irish Government open-data portal, useful for public-sector, transport, environment,
       health and regional datasets.
   •   Central Statistics Office Ireland: official Irish statistical datasets. Confirm that the selected table
       supports a meaningful prediction task rather than only descriptive analysis.
   •   EU Data Portal and other official open-data portals: useful for public datasets with documented
       provenance and reuse conditions.
A suitable dataset should have a clear prediction target, enough usable records and features for model
comparison, manageable size, documented meaning, and a licence that permits academic use. Avoid datasets
containing uncontrolled personal, confidential or highly sensitive information.

Repository Setup
  •   Use the official GitHub Docs: Creating and managing repositories guide to create a repository.
  •   Add a README explaining the project question, dataset source, folder structure, setup steps and exact
      commands required to run the work.
  •   Use a Python .gitignore, following the official GitHub Docs: Ignoring files guide. Do not commit
      virtual environments, passwords, API keys, temporary files or large generated outputs.
  •   Commit regularly using short, meaningful messages. The history should show steady development
      rather than one final upload.
  •   Do not place data in the repository unless its licence permits redistribution. Otherwise, provide
      download and preparation instructions.

Python Environment
  •   Create a separate environment for the project using either Python venv or conda. The official scikit-
      learn installation guide provides current commands for Windows, macOS and Linux.
  •   Install only the packages required by the project and record their versions in requirements.txt or
      environment.yml.
  •   Test the recorded environment by recreating it and running the full workflow from a clean session
      before each milestone.
  •   Record the Python version and any system-specific requirements in the README.

Notebooks and Code
  •   Jupyter Notebook or JupyterLab may be used locally; a hosted notebook such as Google Colab may also
      be used if the work can be reproduced from the submitted files and environment information.
  •   Organise notebooks in a clear sequence: project setup, data loading, audit, preprocessing, modelling,
      evaluation and conclusions.
  •   Use descriptive headings and short explanations, but keep code cells focused and remove abandoned
      experiments.
  •   Restart the kernel and run all cells from top to bottom before submission. The notebook must not
      depend on hidden variables or an undocumented execution order.
  •   Where the workflow becomes lengthy, move reusable functions into Python files and import them into
      the notebook.
